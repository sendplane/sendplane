# ADR-0007 리포지터리 인터페이스 + storetest 적합성 스위트

상태: accepted · 2026-09-20

## 맥락
Postgres와 MongoDB를 기본 제공하고 커스텀 DB도 가능해야 하며, CI에서 두 구현의 동일 기능성을 검증해야 한다.

## 결정
- 도메인 코드는 `store` 인터페이스만 본다. SQL/BSON은 구현 패키지 밖으로 나오지 않는다.
- **다중 문서 트랜잭션을 인터페이스 계약에 넣지 않는다.** 원자성은 (a) 멱등 삽입(유니크 키) (b) CAS 상태 전이 (c) 아웃박스 같은 스토어 삽입으로 얻는다. 이 제약이 Mongo standalone과 커스텀 KV 구현을 가능하게 한다.
- `store/storetest.Run(t, factory)`가 계약 명세다. 새 리포지터리 메서드는 storetest 케이스 없이는 머지하지 않는다. 동시 claim 무중복, lease 만료, 멱등 인제스트, 테넌트 격리, 커서 페이지네이션 안정성을 포함.
- CI는 `services:`로 postgres:16, mongo:7을 띄워 같은 스위트를 매트릭스 실행.

## 기각한 대안
- **ORM/쿼리 빌더로 두 DB 추상화(GORM 등)**: claim 같은 핵심 쿼리는 DB별로 다르게 써야 성능이 나온다. 추상화가 오히려 방해.
- **Mongo 트랜잭션 사용**: 레플리카셋 필수 요구가 생기고 커스텀 구현 부담이 커진다.

## 결과
- 리포지터리 수가 많아 보일러플레이트가 있지만, 구현당 storetest가 회귀를 잡는다.
- 커스텀 DB 구현자는 storetest를 통과시키면 된다는 명확한 기준을 갖는다.
