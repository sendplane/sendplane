# ADR-0015 메일박스 헬스는 프로브/바운스 결과와 분리

상태: accepted · 2026-09-22

## 맥락

프로브 메일박스와 바운스 메일박스는 운영자가 자격증명을 넣어 두고 잊어버리는 IMAP/POP3 계정이다.
비밀번호 로테이션, 만료된 앱 비밀번호, 2FA 전환, 폴더 이름 변경 — 전부 **조용히** 계정을 죽인다.

문제는 그 침묵이 침묵으로 끝나지 않는다는 것이다. 지금까지 이 실패는 다른 신호로 위장해서 나타났다.

- 프로브 메일박스에 로그인할 수 없으면 프로브 메일을 회수하지 못하고, 15분 타임아웃이 지나면 run이
  red "메일이 도착하지 않았습니다"로 닫힌다. 그 sender는 red가 되고, 운영자는 **SPF·DKIM·DMARC·PTR을
  뒤지기 시작한다.** 실제 원인은 IMAP 비밀번호다.
- 바운스 메일박스가 로그인을 거절하면 폴러 로그에 에러가 쌓이는 것 말고는 아무 일도 일어나지 않는다.
  DSN은 계속 쌓이고, hard bounce는 suppression에 들어가지 않고, 평판은 조용히 깎인다.

또한 생성 시점에 자격증명이 맞는지 확인할 방법이 아예 없었다. 저장하고, 6시간 뒤 프로브가 실패하거나
1분 뒤 폴러 로그를 직접 열어 보는 것이 전부였다.

## 결정

**메일박스의 도달 가능성을 1급 상태로 분리한다.** 프로브 판정(`HealthStatus` green/yellow/red)과도,
바운스 이벤트와도 별개의 필드다.

- `store.MailboxHealth{Status, Stage, Reason, CheckedAt, LastOKAt, ConsecutiveFailures}` 를
  `ProbeMailbox` 와 `BounceMailbox` 가 **똑같이** 갖는다. 두 메일박스는 하는 일이 다르지만
  고장 나는 방식은 같다.
- 상태는 `MailboxStatus` = `unknown|ok|error`. green/yellow/red 를 재사용하지 않는다. 거절된 로그인에
  "yellow 버전"은 없고, 같은 어휘를 쓰면 화면에서 두 개가 섞인다.
- `Stage` = `config|dial|tls|auth|folder|ok`. **`auth` 를 네트워크 실패와 구분하는 것이 이 결정의 핵심**이다:
  고칠 사람과 고칠 방법이 다르다.
- 쓰기는 `UpdateHealth` 전용. 낙관적 동시성에 참여하지 않고 `version`/`updated_at` 도 건드리지 않는다 —
  background 점검이 운영자의 편집을 떨어뜨리거나 편집에 떨어져서는 안 된다.
- `internal/mbhealth` 가 전이 규칙의 단일 출처다. 네 곳(바운스 폴러, 프로브 수집, `mailbox-check` 루프,
  테스트 엔드포인트)이 같은 관찰을 하고, 규칙을 네 번 쓰면 둘은 반드시 어긋난다.

**프로브 run 은 메일박스를 못 열었으면 판정하지 않는다.** 그런 run 은 `unknown` +
`probe mailbox unreachable: {stage}` 로 닫히고, 연속 미수신 카운트에도 들어가지 않는다. sender 요약이
그 사유를 그대로 물고 가므로 화면에 원인이 보인다.

**`mailbox-check` 리더 루프**(`AllTenants`, 기본 15분)를 둔다. 나머지 세 주체는 전부 다른 일의 부산물이다:
바운스 폴링은 꺼져 있을 수 있고, 프로브 수집은 6시간에 몇 분만 메일박스를 본다.

**테스트 엔드포인트 두 쌍.** 저장 전(`POST .../test`, 본문의 자격증명)과 저장 후(`POST .../{id}/test`,
저장된 행 + 헬스 기록). 원격 실패는 `200` + `ok:false` 다.

## 기각한 대안

- **`HealthStatus` 재사용**: 프로브 판정과 같은 필드에 섞으면 "이 red 는 배달 문제인가 로그인 문제인가"를
  구분할 수 없다. 이 ADR이 고치려는 혼동을 필드 하나에 그대로 인코딩하는 셈이다.
- **로그만 남기기**: 지금이 그렇다. 아무도 폴러 로그를 보지 않는다.
- **첫 실패에서 바로 이벤트**: IMAP 서버 재시작 한 번, 커넥션 리셋 한 번에 알림이 간다. 연속 2회로
  blip 을 걸러낸다(저장된 `Status` 는 1회에서 바로 뒤집는다 — 뱃지는 거짓말하면 안 된다).
- **테스트 실패를 4xx/5xx 로**: 거절된 로그인은 요청의 답이지 요청의 실패가 아니다. 4xx 로 주면
  프런트가 "요청 실패"를 띄우고 `stage` 는 에러 본문에 파묻힌다.
- **`{id}/test` 의 본문 비밀번호로도 헬스를 쓰기**: 폼의 오타가 멀쩡한 메일박스를 고장 난 것으로 만든다.
  그 호출은 "이 비밀번호가 될까"를 묻는 것이지 "이 메일박스가 살아 있나"를 묻는 게 아니다.

## 결과

- 마이그레이션 `0004_mailbox_health.sql` 이 두 테이블에 6개 컬럼을 더한다. 기존 행은 `unknown` 으로
  시작하고 첫 점검에서 채워진다.
- 새 이벤트 `mailbox.unhealthy` / `mailbox.recovered`. 한 메일박스당 한 장애에 한 번이므로
  `DefaultOffEventTypes` 에 넣지 않는다 — 기본 구독이다.
- `probe.mailbox_check_interval`(기본 15분)이 설정에 추가된다. 이 루프는 `probe.enabled` 와 무관하게
  돈다: 바운스 메일박스도 같은 감시가 필요하고, 프로브를 안 쓰는 배포에도 만료되는 자격증명은 있다.
- 메일박스 점검은 **실제 로그인**이다. 프로바이더가 로그인 빈도를 제한할 수 있으므로 기본 간격을
  분 단위가 아니라 15분으로, 틱당 20개로 묶어 둔다.
